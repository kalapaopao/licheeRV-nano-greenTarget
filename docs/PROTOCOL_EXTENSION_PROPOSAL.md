# 串口协议扩展提案（TLV 扩展块 + 时间戳）

> 状态：**提案**，未实施。需要电控配合改固件。
> 目的：一次改动解决三件事——① 电控帧能对时；② 以后加字段不用再改协议；③ 旧版本仍能解析。
> 前提：现有 0x01/0x02 帧格式**不破坏**，只是把"以后要新加的东西"放进一个可跳过的扩展块。

---

## 1. 为什么现在需要改

| 现状 | 后果 |
|---|---|
| 0x02 帧**没有时间戳**，只有帧序号 | 视觉侧只能用"收到它的本地时刻"近似它产生的时刻；误差 = 串口传输 2.9 ms + 电控采样相位 0~10 ms。这是现在所有"配对/年龄"复杂度的根源 |
| 26 字节 payload **已经占满** | 想加舵机指令、加速度、事件位，只能改 `LEN` —— 双方解析器同时改，且旧固件/旧视觉程序会直接解析失败 |
| `SEQ` 只做丢包统计，不回显 | 无法把"我们发的那一帧"和"电控的那一帧"对应起来，也测不出往返延迟 |

## 2. 方案：帧尾追加 TLV 扩展块（向后兼容）

```
A5 5A | LEN | SEQ | CMD | PAYLOAD(LEN 字节) | [EXT] | CRC_L CRC_H
                                    ↑
                        LEN = 0x1A + len(EXT)     （原来只有 0x1A）
```

- `EXT` **可以完全不存在**（旧格式，LEN=0x1A）→ 新解析器照旧能解析；
- `EXT` 存在时，第一个字节是 `EXT_LEN`，后面是若干 TLV：
  `TAG(u8) | LEN(u8) | VALUE[LEN]`；
- **CRC 覆盖从 offset 2 到 payload 末尾（含 EXT）**，算法不变；
- 解析器遇到**不认识的 TAG 直接跳过**（这就是"通用"的关键：以后加字段不用再改协议）。

### 2.1 建议先定义的三个 TAG

| TAG | LEN | 含义 | 为什么 |
|---|---|---|---|
| `0x01` | 4 | `u32` 电控毫秒计时（上电清零，自然回绕） | **最重要**：视觉侧用它做时钟对齐 |
| `0x02` | 1 | 事件位：bit0 起飞、bit1 落地（粘滞，电平型） | 比 `STATE` 边沿更明确，不怕中间丢帧 |
| `0x03` | 8 | 4 路舵机指令，`int16` × 4（0.1% 占空比 或 0.1° 期望角） | 你想要的"电机怎么转" |

> `0x03` 是你要的"舵机数据"。`int16` 足够覆盖 −100%~100% 或 −180°~180°，8 字节 100Hz = 800 B/s。

## 3. 视觉侧怎么用 `TAG 0x01`（时间戳）做对时

收到每帧都记一对样本 `(mcu_tick, 本地 rx_us)`。两者的关系是线性的
`本地时刻 ≈ tick + offset`，所以：

```
offset 用最近 8~16 个样本做最小二乘估计（或者简单地取 (rx_us - tick) 的中位数）
```

- 串口传输 + 中断延迟 ≈ 常数（2.9 ms + 几十微秒），被 offset 吸收；
- 电控 tick 抖动、我们 poll 唤醒抖动 → 中位数/回归能压到 **±1 ms** 以内；
- 若 `tick` 突然跳变（电控重启），检测到残差突变就**重拟合**。

于是"某一帧画面用的电控数据有多旧"从 **±10 ms 的估计**变成 **±1 ms 的测量**，
并且不再依赖"接收时刻 ≈ 产生时刻"这个假设。

## 4. 两边各要改多少

| 侧 | 改动 | 量 |
|---|---|---|
| 电控（发送 0x02） | 在 payload 后追加 `EXT_LEN=5, 01,04,<u32 tick>`；`LEN = 0x1A+6`；CRC 覆盖范围不变（本来就从 offset 2 到最后） | ~20 行 |
| 电控（解析我们的 0x01） | 无需改（我们不追加 EXT 时 LEN 仍是 0x15） | 0 |
| 视觉（解析 0x02） | 解析器允许 `LEN >= 0x1A`，读 EXT；不认识就跳过 | ~40 行 |
| 视觉（发送 0x01） | 建议对称：追加 `EXT_LEN=5, 01,04,<u32 相对时间>`，让电控也能对时 | ~20 行 |

**带宽**：多 6 字节/帧 × 100 Hz = 600 B/s。115200 下从 29% → **~34%**，仍然宽裕。

## 5. 兼容性检查表（改之前的底线）

- [ ] 旧视觉程序收到带 EXT 的 0x02：**会解析失败**（它按固定 33 字节校验 `LEN=0x1A`）。
      → 所以视觉侧要**先**升级到"允许 LEN ≥ 0x1A"，电控**后**发 EXT。顺序不能反。
- [ ] 旧电控固件收到带 EXT 的 0x01：同样会失败 → 先给电控发一版"允许 LEN ≥ 0x15"的解析器。
- [ ] 两侧都必须"未知 TAG 跳过"，否则以后加字段又要双改。
- [ ] 保留位 `FLAGS.bit3~7` 仍然空着：如果只需要一个"起飞事件"标志，**零成本**先加在 bit3，
      不必等 TLV（但时间戳没地方放，还是得靠 TLV）。

## 6. 落地顺序（建议）

1. **先做零成本的**：电控把 `FLAGS.bit3` 定义为"TAKEOFF 粘滞位"（不改长度、不改 CRC 范围）。
2. **视觉侧先升级**：解析器容忍 `LEN ≥ 0x1A` 和未知 TAG（向后兼容，不改行为）。
3. **电控再发 EXT**：先只加 `TAG 0x01 = tick`。
4. 我们在 `frames.csv` 里把 `mcu_age_us` 从"接收时刻差"换成"真时间差"，并记录拟合残差；
   若残差 > 5 ms 打一行告警（说明对时不可信）。
5. 有需要再加 `0x02`（事件位）/`0x03`（舵机）。

## 7. 如果电控短期改不了，退而求其次

| 做法 | 精度 | 代价 |
|---|---|---|
| 现状：用接收时刻当产生时刻 | ±10 ms | 0 |
| 电控在**上电时**发一次 tick、之后不再发 | 无法对时（时钟会漂） | ✗ 不可行 |
| 电控把 `SEQ` 当"时间戳低字节"（每 1 ms +1） | ±1 ms，但改语义、可能溢出 | 不建议 |
| 我们做一次**联调实验**测固定 offset（用 FLAGS bit3 打点） | ±2~3 ms，但只对那一次温度/电压有效 | 一次性校准，非长期 |
