# 串口协议（视觉 → 电控）

> 本文档给电控同学看。视觉侧实现：`src/uart_out.cpp`。
> 所有参数在 `config.yaml` 里可改，改完重启生效。

---

## 一、物理层

| 项 | 值 | 备注 |
|---|---|---|
| 设备 | `/dev/ttyS1`（可配 `uart_device`） | ⚠️ **不是 ttyS0**：S0 是内核 console，被 getty 占用 |
| 波特率 | 115200（可配 `uart_baud`） | 8N1，无流控，raw 模式 |
| 电平 | 3.3V TTL | 接线注意 TX/RX 交叉、共地 |
| 发送频率 | 50 Hz（可配 `uart_rate_hz`） | **固定节奏发送，没目标也发** |

**接线**：视觉板 `ttyS1 TX` → 电控 `RX`；视觉板 `ttyS1 RX` → 电控 `TX`；GND 共地。
（视觉侧目前只发不收，RX 可不接。）

⚠️ **硬件待确认**：LicheeRV Nano 排针上实际引出的是哪几个 UART，需要对照原理图确认。
设备树里有 ttyS0~ttyS4 五个节点，但排针未必都引出。若 ttyS1 不通，可改
`uart_device` 试 ttyS2/ttyS3/ttyS4。

## 二、帧格式（ASCII）

```
$GT,<det>,<yaw>,<pitch>,<vyaw>,<vpitch>,<dist>,<age>,<seq>,<state>*<CS>\r\n
```

### 2.1 字段表

| 字段 | 类型 | 单位 | 说明 |
|---|---|---|---|
| `det` | 0/1 | — | 1 = 有目标（confirmed 或 coasting）；0 = 无目标 |
| `yaw` | float | 度 | 水平角，**正 = 目标在光轴右侧** |
| `pitch` | float | 度 | 俯仰角，**正 = 目标在光轴上方** |
| `vyaw` | float | 度/秒 | 水平角速度（给电控做前馈） |
| `vpitch` | float | 度/秒 | 俯仰角速度 |
| `dist` | float | 米 | 斜距；`distance_valid=false` 时为 `0.000` |
| `age` | int | 毫秒 | 距最近一次**真实检测**的时长（跟踪器内部量）；`-1` = 从未检测到。coast 期间它会持续增长，这是设计行为——**它不是**「这一帧从取到图像到发出去」的延迟 |
| `seq` | uint | — | 递增序号（每次状态更新 +1），用于丢帧检测 |
| `state` | 0/1/2 | — | 0=lost 1=coasting 2=confirmed |
| `CS` | hex | — | `$` 与 `*` 之间所有字符的 XOR，两位大写十六进制 |

### 2.2 实例

**无目标（视觉在线，但没看到东西）**：

```
$GT,0,0.00,0.00,0.00,0.00,0.000,-1,0,0*02
```

**已确认，目标在右上方**：

```
$GT,1,12.34,5.67,45.20,-12.30,3.456,8,1234,2*5A
```

**跟丢但仍在预测（coast）**：

```
$GT,1,12.50,5.60,30.10,-10.00,3.400,120,1240,1*3F
```

### 2.3 校验和计算

```c
// 对 '$' 之后、'*' 之前的每一个字节做 XOR
uint8_t cs = 0;
for (const char* p = body_start; p < star_pos; ++p) cs ^= (uint8_t)*p;
```

Python 参考实现：

```python
body = '1,12.34,5.67,45.20,-12.30,3.456,8,1234,2'
cs = 0
for ch in body: cs ^= ord(ch)
print('$GT,%s*%02X\r\n' % (body, cs))   # $GT,1,...,2*5A
```

**建议电控侧**：校验失败的帧丢弃，但**不重置状态**（偶发误码不应导致目标丢失）。

## 三、电控侧使用建议

### 3.1 三个状态的区别

| state | det | 含义 | 电控该怎么用 |
|---|---|---|---|
| 2 `confirmed` | 1 | 连续命中 ≥ `sel_confirm_frames`（默认 5 帧） | **可以闭环** |
| 1 `coasting` | 1 | 短暂跟丢，用卡尔曼预测继续输出 | **可以继续跟，但要准备丢** |
| 0 `lost` | 0 | 跟丢超过 `sel_lost_frames`（默认 10 帧） | **停止闭环**，进入搜索 |

**为什么要有 coasting**：目标被手挡一下、或闪一下没检测到，如果立刻报 lost，
云台会突然停/抖。coast 让它在 ~10 帧（125ms @80fps）内保持输出。

### 3.2 必须看 `age`（数据新鲜度）

**这是最重要的健壮性设计。** `det` 只能说明「视觉认为有目标」，
不能说明「这个数据是新鲜的」。

```
age < 50ms      → 数据新鲜，可闭环
age 50~200ms    → 视觉变慢或降频，谨慎
age > 200ms     → 数据陈旧，停止闭环
age = -1        → 从未检测到
```

**典型故障场景**：视觉程序崩溃/卡死 → 串口帧停止 → 电控收不到任何数据。
**所以电控侧必须有超时保护**：超过 300ms 没收到任何帧 → 视为视觉掉线 → 安全停机。

> ⚠️ **`age` 与「板端发送年龄」是两个不同的量，不要混用**：
> - `age`（协议字段）：这份角度数据离**最近一次真实检测**多久了 —— 电控用它判断
>   「数据是否陈旧」。coast 期（state=1，角度是卡尔曼外推）它会持续增长，正是要
>   让电控知道「越久越该收手」。
> - `uart_age_*`（视觉侧日志，**不占协议字段**）：这一帧从「程序取到图像」到
>   「串口真正发出去」的板端延迟 —— 用来评估视觉链路自身的实时性，见第六节。

### 3.3 `v_yaw` / `v_pitch` 怎么用

这两个是卡尔曼滤波器的速度状态，已经平滑过：

```
预测量 = 当前位置 + v_yaw × 0.001        （10ms 后的位置）
```

**建议用法**（前馈补偿串口延迟）：

```
yaw_target = yaw + v_yaw * (你的控制周期秒数)
```

⚠️ 注意：`v_yaw` 在 `coasting` 期间是**预测值**，目标真的消失时会慢慢衰减，
不是真实测量。别在 coast 期用太久。

### 3.4 `seq` 用来发现丢帧

```
if (seq != last_seq + 1 && seq != last_seq)  →  中间丢了 (seq - last_seq - 1) 帧
```

由于是固定 50Hz 发送，如果 `seq` 在一段固定时间里没变，说明
**视觉没有更新结果**（可能降频了），这时 `age` 也会同步增长。
两个信号互相印证。

## 四、参数调整（视觉侧）

全部在 `config.yaml`：

```yaml
uart_enable: false        # 总开关。默认 false，联调时改 true
uart_device: /dev/ttyS1
uart_baud: 115200
uart_rate_hz: 50          # 发送频率，1..200
```

⚠️ **`uart_enable: true` 时如果设备打不开，程序会直接退出（返回码 3）**，
不会静默降级。这是故意的：联调时「收不到数据」比「启动失败」更难排查。
需要纯视觉模式时把 `uart_enable` 设回 false。

## 五、带宽核算

单帧长度：`$GT,` (4) + body + `*` (1) + CS (2) + `\r\n` (2)

body 最长约 50 字符（所有字段取最大宽度）→ 单帧约 60 字节。

```
115200 baud, 8N1 → 有效 11520 字节/秒
60 字节 × 50 Hz = 3000 字节/秒 ≈ 26% 占用
```

**余量充足**。如需提高频率到 100Hz，占用约 52%，仍然可以。

## 六、视觉侧诊断日志（联调时对照用）

这些行打在视觉板 stdout（`start.sh` 的日志文件里），**不通过串口发给电控**，用于核对
「采集 → 检测 → 发送」这条链路到底慢在哪。所有时间都是 `CLOCK_MONOTONIC` 微秒，
只做差、不做绝对时间。`capture_mono_us` 是「程序拿到这一帧」的时刻，**不是曝光时刻**。

| 日志行 | 关键字段 | 含义 |
|---|---|---|
| `capture_frames= host_fps= pts_fps= duplicate_pts= timeouts=` | 采集帧率 / 按 PTS 推算的帧率 / 重复 PTS 次数 / 取帧超时次数 | 80fps 是否达成、PTS 是否单调 |
| `DETECT avg_ms= max_ms= proc_avg_ms= proc_max_ms= lat_avg_ms= lat_max_ms= calls=` | `avg/max` = 抽样→发布整块；`proc` = 抽样→结果完成；`lat` = **取帧**→结果完成 | 视觉处理耗时与「取帧到出结果」的延迟 |
| `TIMING last_frame_id= last_pub_frame_id= last_capture_age_ms= uart_age_last= uart_age_avg= uart_age_max= uart_age_n=` | 相机帧号 / 最近发布帧的年龄 / **串口发送时重算的「取帧→发送」年龄** | 结果是否还在更新；串口真正发出去的数据有多旧 |
| `PTS_STAT last_raw= window_delta_raw= per_frame_raw= duplicate_pts=` | VI 原始 PTS、窗口内差值、每帧差值 | **只观测，不假设单位**：若单位是微秒，80fps 时 `per_frame_raw≈12500` |
| `UART sent= rate= errors=` | 发送帧率 / 写失败次数 | 串口链路是否健康 |
| `GREEN_TARGET ... age=... frame=` | 协议里的 `age`、角度/角速度/距离、帧号 | 限频到 ≤10Hz，用于人工对照 |

三条纪律：
1. `GREEN_TARGET` 最多 10Hz（连续目标时不再每帧 printf），其余统计行每 5 秒一次；
2. `age`（协议字段，数据陈旧度）与 `uart_age_*`（板端端到端延迟）**不是同一个量**，
   前者发给电控，后者只进日志；
3. `frame_id` 是相机帧号（每取到一帧 +1），`seq` 是结果序号（跟踪器每次更新 +1），
   两者不能互相替代。

> **2026-11-08 板端实测（1280×720 / 80fps / `detect_stride=1`）**：
> `per_frame_raw` 稳定在 12500±130，`window_delta_raw` 约 5,000,000/5s，
> `duplicate_pts=0` → **`u64PTS` 单位是微秒**且单调递增。代码仍然只记录、
> 不把 PTS 参与任何计算（换传感器或换驱动后需重新确认）。
> 同一次实测：`proc_avg_ms≈5.1`、`lat_avg_ms≈5.1`（display 关闭时），
> `uart_age_avg≈11.5ms`（50Hz 发送 + 80Hz 出结果，平均要等半个帧周期）。

## 七、待电控确认的事项

| # | 问题 | 影响 |
|---|---|---|
| 1 | 接收方用 UART 还是 CAN/SPI？ | 决定要不要换物理层 |
| 2 | 波特率是否固定 115200？还是用 921600 提高余量 | 影响 `uart_baud` |
| 3 | 需要**角度**还是**像素**？（本协议给角度） | 若要像素需改协议 |
| 4 | 是否需要 `dist`？不需要可以省掉，减轻解析负担 | 影响协议长度 |
| 5 | 是否接受 ASCII？还是要求二进制紧凑帧 | 二进制帧可省 60% 带宽 |
| 6 | 有没有现成的帧格式/校验方式（如 CRC16） | 如有需适配 |
| 7 | 视觉板排针引出了哪个 UART | 决定 `uart_device` |
| 8 | 电控侧期待的最小发送频率 | 影响 `uart_rate_hz` |
| 9 | 是否需要在协议里增加「取帧→发送」年龄字段（如 `age_uart`）？ | 需要加字段；当前只写日志，不改字段数量/顺序 |

**在得到回复前，本协议可以先用起来**：ASCII 便于抓包分析，改协议只需改
`format_ascii()` 一个函数。
